# Phase 6: User Interface (UI) Design & Usability Engineering — QuickBite

## 1. Usability Philosophy & Design Standards
QuickBite follows the **Eight Golden Rules of Interface Design** (Shneiderman) and **Nielsen's 10 Usability Heuristics**:
- **Clean Aesthetic**: Crisp light corporate theme with clean slate typography, warm orange/crimson accents (`#E65100` / `#D84315`), subtle cards, and high contrast ratios conforming to WCAG 2.1 AA standards. Avoids dreary pitch-black dark modes.
- **Error Prevention & Visibility**: Real-time validation badges, explicit disabled buttons for invalid forms, step indicators for checkout, and live visual breadcrumbs for order progression.
- **Fail-Safe Defaults**: Explicit confirmation dialogs for destructive actions (e.g., cancelling an order), with clear feedback upon completion.

## 2. Screen Specifications

### Screen 1: Login & Registration Screen
- **User**: Unauthenticated Diners, Restaurant Staff, and Platform Administrators.
- **Goal**: Establish authenticated session with appropriate role context.
- **Navigation**: Accessible from landing page header; toggles cleanly between "Login" and "Register".
- **Inputs**:
  - Registration: Full Name, Email Address, Password (with live strength meter), Confirm Password, Role Selector (Customer / Staff).
  - Login: Email Address, Password.
- **Feedback**:
  - Live password strength indicator (length, numbers, uppercase, special character).
  - Spinner on submission; success toast upon token issuance with instant role-based redirect.
- **Error Handling**:
  - Generic authentication error message ("Invalid email or password") to prevent username enumeration.
  - Rate-limit countdown warning if threshold exceeded.
- **Security Controls**:
  - Client-side pre-validation + server-side bcrypt verification.
  - Automatic masking of password fields (`type="password"`).
  - Token stored in secure session storage/memory with short-lived TTL.

---

### Screen 2: Customer Restaurant & Food Browsing Screen
- **User**: Authenticated or Guest Customer.
- **Goal**: Browse active restaurants, search cuisine, view available food items with canonical prices.
- **Navigation**: Primary landing view (`/browse`); top navigation bar with category filters and active cart badge.
- **Inputs**: Search query bar (debounced), cuisine category filter pills, restaurant selection cards.
- **Feedback**:
  - Visual badges for dietary tags (Veg, Non-Veg, Chef's Special).
  - "Out of Stock" greyed-out badge for unavailable dishes with disabled "Add to Cart" button.
  - Subtle ripple animation and badge count update on cart icon when an item is added.
- **Error Handling**:
  - Empty state graphic with "No restaurants found matching your query" and quick-clear filter button.
- **Security Controls**:
  - HTML entity encoding on all food descriptions to prevent Cross-Site Scripting (XSS).
  - Server-side filtering ensuring inactive/closed restaurants are never rendered.

---

### Screen 3: Cart & Checkout Screen
- **User**: Customer with items in cart.
- **Goal**: Review selected food items, adjust quantities, input delivery address, provide payment token, and execute checkout.
- **Navigation**: Accessible via Cart button; breadcrumb: `Browse → Cart → Checkout`.
- **Inputs**:
  - Item Quantity Increment/Decrement controls ($1..99$).
  - Delivery Street Address, Apt/Suite, Contact Phone Number.
  - Payment Token Selection / Test Card Token selector (`tok_visa_valid`, `tok_mastercard_valid`, `tok_declined`).
- **Feedback**:
  - Itemized breakdown: Subtotal, Estimated Tax (10%), Flat Delivery Fee ($3.00), Grand Total.
  - Informational alert stating: *"Final price is computed authoritatively by our secure backend servers."*
- **Error Handling**:
  - If payment simulation fails, displays alert: *"Payment transaction declined by issuer. Your cart has been preserved. Please retry."*
- **Security Controls**:
  - Client cannot modify price field (read-only UI label).
  - Zero input fields for raw credit card numbers or CVVs (PCI compliance).
  - Prevent double submission by disabling "Place Order" button immediately upon click.

---

### Screen 4: Live Order Status Tracking Screen
- **User**: Customer monitoring their placed order.
- **Goal**: Observe real-time preparation progress and cancel order if eligible.
- **Navigation**: Redirected here post-checkout; accessible from "My Orders" tab.
- **Inputs**: "Cancel Order" button (active ONLY when status is `PLACED`).
- **Feedback**:
  - Multi-step visual stepper:
    $$\text{Placed} \longrightarrow \text{Accepted} \longrightarrow \text{Kitchen Preparing} \longrightarrow \text{Out for Delivery} \longrightarrow \text{Delivered}$$
  - Dynamic status badge with color coding (Green for Delivered, Blue for Preparing, Red for Cancelled/Rejected).
- **Error Handling**:
  - If cancellation attempted after staff accepted: modal alert *"Order has already begun preparation by kitchen staff and cannot be cancelled."*
- **Security Controls**:
  - Strict customer ID validation (prevents viewing or cancelling unauthorized orders).
  - Status polling over authenticated HTTPS requests.

---

### Screen 5: Restaurant Staff Dashboard & Kitchen Orders Screen
- **User**: Restaurant Staff assigned to a specific branch.
- **Goal**: Monitor real-time queue of incoming orders for the kitchen.
- **Navigation**: Top navigation `/staff/dashboard` (restricted to staff role).
- **Inputs**: Order status transition buttons (`Accept Order`, `Reject`, `Start Cooking`, `Mark Dispatched`).
- **Feedback**:
  - Real-time audible ping or visual pulse badge on new incoming `PLACED` orders.
  - Order cards showing elapsed time, customer first name, delivery address, ordered items with quantities.
- **Error Handling**:
  - Warning notification if staff attempts invalid state transition.
- **Security Controls**:
  - Tenant scoping: Dashboard queries backend with staff JWT; backend strictly returns orders matching `staff.restaurant_id`.
  - Disables administrative and customer routes.

---

### Screen 6: Menu Management Screen (Staff)
- **User**: Restaurant Staff.
- **Goal**: Add new dishes, modify prices, toggle item availability (in-stock / 86'd).
- **Navigation**: Staff portal secondary tab: `Menu Management`.
- **Inputs**: Dish Name, Description, Category, Canonical Price ($), Availability Toggle (Checkbox).
- **Feedback**:
  - Toast confirmation: *"Price updated successfully. Changes applied to all future orders."*
  - Instant toggle switch without requiring full page refresh.
- **Error Handling**:
  - Input rejection if price $\le 0$ or non-numeric: *"Price must be a valid positive currency amount."*
- **Security Controls**:
  - Staff can only edit menu items belonging to their assigned restaurant.
  - Every price change automatically generates an audit log record (`MENU_PRICE_CHANGED`).

---

### Screen 7: Order Management & Historical Review Screen
- **User**: Staff and Customer (scoped to respective permissions).
- **Goal**: Review comprehensive receipts, past order timestamps, and items.
- **Navigation**: `/orders/history` tab in header.
- **Inputs**: Date range filter, status filter dropdown.
- **Feedback**:
  - Tabular view with Order ID, Date/Time, Restaurant, Item Summary, Total Paid, and Final Status.
- **Error Handling**:
  - Clear message when no past orders match query.
- **Security Controls**:
  - Data minimization: Customer sees only their own history. Staff sees only their restaurant's history. Admin sees audit trail.

---

### Screen 8: Platform Governance & Audit Log Viewer (Admin)
- **User**: Platform Administrator.
- **Goal**: Inspect security events, audit unauthorized attempts, review system health.
- **Navigation**: `/admin/audit` (accessible only with `role == admin`).
- **Inputs**: Event filter (Logins, Authz Failures, Price Changes, Orders), Search IP.
- **Feedback**:
  - Visual security badges: Green for `SUCCESS`, Red for `FAILURE / UNAUTHORIZED`.
- **Error Handling**:
  - Graceful fallback if audit database is under heavy read load.
- **Security Controls**:
  - Strict RBAC check (HTTP 403 for non-admins). Read-only data presentation.
